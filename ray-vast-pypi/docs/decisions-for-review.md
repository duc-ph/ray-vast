# Decisions for review

Technical decisions made while the user was away. Rule: simplest option that works, no compromise on reliability, no fragility. Each line: date, decision, reason, where.

- 2026-10-13 — The wheel is pure Python (`py3-none-any`) but carries the x86_64 Linux shim `.so` as package data. Reason: the `.so` is loaded only by `LD_PRELOAD` inside Linux containers, never imported; one wheel for all platforms. (Step 1)
- 2026-10-13 — The sdist includes only `src`, `tests`, `scripts` and the top-level files, not `docs/` or `spikes/`. Reason: keep spike logs out of the published package. (Step 1)
- 2026-10-13 — The packaging test installs the wheel with `--no-deps` and builds with `--no-isolation`. Reason: fast and offline; the CLI entry point needs only the stdlib to show `--help`. (Step 1)
- 2026-10-13 — Code review is run per step for steps with logic; step 1 (packaging only) is reviewed together with step 2. Reason: a skeleton has nothing for the Spec/Standards axes to find.
- 2026-10-13 — `create_instance` retries only on HTTP 429, not on 5xx or connection errors. Reason: a lost reply may already have rented the offer; a retry could rent twice. A rental that we did not record is found by the outside check (label sweep) and destroyed. (Step 3)
- 2026-10-13 — vast retries: 5 tries, backoff 1-2-4-8 s with jitter, 30 s timeout per call. A destroy of an instance that is already gone (404) is a success. (Step 3)
- 2026-10-13 — `max_dollars_per_hour` is required (no default). Reason: a missing budget must not mean "no limit". `node_config.disk_gb` defaults to 50. (Step 2)
- 2026-10-13 — A user filter on an added field (`cpu_cores_effective`, `direct_port_count`) is allowed when it is at least as strict, and it is merged; `num_gpus` must equal `GPU`. Reason: lets one node type per CPU size (`{gte: 8, lt: 16}`). (Step 2)
- 2026-10-13 — The vast key is not a config field. The CLI reads it from `VAST_API_KEY` or `~/.config/vastai/vast_api_key` (the vast CLI's file). Reason: keeps the secret out of the cluster YAML. The field is `cert_max_age_days` (plan said `cert_max_age`), for a clear unit. (Step 2 review)
- 2026-10-13 — Provider fields other than `region`, `image` and `max_dollars_per_hour` have defaults (`candidate_factor` 2, `cert_max_age_days` 365, `allow_non_datacenter` false, `order_by` `dph_total`, `head_instance_type` `t3.large`). (Step 2 review)
- 2026-10-13 — The packaging test does not install the full Ray dependency set in a clean venv (it uses `--no-deps`). Reason: Ray is large; the full install is exercised by the head container in step 10 and the end-to-end tests. (Step 1 review)
- 2026-10-13 — PKI: RSA-2048 keys (proven with Ray gRPC in C0–C4); leaf certs have serverAuth + clientAuth; `not_before` is 5 min in the past (worker clock skew); CA `pathlen:0`; `cryptography>=42`. (Step 4)
- 2026-10-13 — Fingerprint = SHA-256 of the CA cert's DER bytes, lowercase hex (S5). (Step 4)
- 2026-10-13 — The head server uses two ports: plain TLS (download, enrollment) and mTLS (heartbeat, reports). Reason: one TLS context cannot require client certs for only some paths (S5).
- 2026-10-13 — State: the head is not stored in `ClusterState`; the provider adds the fixed `head` entry (F10). A worker stays in `candidates` after enrollment (with `Slot.instance_id` set) until destroyed, so `total_dph` covers candidates and workers. `ip_ref_remove` stops at 0 (cleanup never raises). Slot IDs `slot-<n>-<hex6>`. (Step 5)
- 2026-10-13 — vast GET and DELETE calls also retry on connection errors (not only 429/5xx). `create_instance(…, disk_gb)` takes the disk size from `node_config.disk_gb`. `search_offers` sends `type: on-demand` and `limit` 100. (Step 3 review)
- 2026-10-13 — Cert files `ca.pem`/`head.pem` are mode 644 (public); keys and the token are 600; the head files directory is 700. A leaf cert never outlives the CA, so the expiry warning checks only the CA. (Step 4 review)
- 2026-10-13 — One security group per cluster. The worker-IP limit is the AWS per-group rule quota (default 60, so about 59 worker IPs with the SSH rule); ray-vast does not hard-code a number. When AWS refuses a rule, the candidate is destroyed and the error says to raise the quota in AWS Service Quotas. (Step 6; design.md said 299 with 5 groups — simplified.)
- 2026-10-13 — Head self-healing: the head container runs `ray start --head --block` with `docker run --restart unless-stopped`. Reason: S2 showed that Ray never restarts a dead monitor; with `--block` the whole head stops and Docker starts a fresh one, which sweeps old workers and scales again. The CA/token/certs persist in the mounted directory and are reused. (S2)
- 2026-10-13 — SG method names are `allow_ip`/`revoke_ip`/`revoke_all` (plan said add/remove). Slot IDs are strings `slot-<n>-<hex6>` (plan said integers; v2 matches by `RAY_CLOUD_INSTANCE_ID`, any string works). A candidate's `public_ip` is set once when vast first reports it running and is never refreshed; the provider compares it with vast's current IP to detect an IP change. (Steps 5–6 review)
- 2026-10-13 — Head server: cheap `/enroll` refusals (unknown instance, already enrolled, wrong source IP, empty key) give 403 without a destroy, so a stranger who knows an instance ID cannot kill a candidate; refusals after the vast key check destroy the candidate. A failed key check does not blocklist the host; failed host checks block as `security` (caps, netns, shm) or `network` (egress, outside port check). Port-A `/report` is log-only. `num_workers_soft_limit = min(cpu_count, 58)`. (Step 8)
- 2026-10-13 — Security (step 8 review): a bad or unknown container key (vast 401/403/404) gives 403 WITHOUT a destroy, and a vast outage gives 503 (the worker retries). Reason: a co-tenant behind the same NAT IP could otherwise kill our candidates with junk keys and guessed instance IDs. Failing candidates are ended by the provider's timeouts instead.
- 2026-10-13 — Security: node certs carry a URI SAN `rayvast:instance/<id>`; port B checks it and the IP SAN. Reason: IP-only certs let a worker (or a former holder of a re-rented IP) send heartbeats or a failed token check for another instance on the same IP. Also: 64 distinct ports required; the node cert is made before the instance is marked enrolled.
- 2026-10-13 — Provider: one "request" = the slots from one create call; its candidates are spread over its slots; when every slot of a request is filled, its other unenrolled candidates are destroyed. Pull limit = `2 × image_size_gb × 8000 / inet_down` s, clamped to 5–15 min (15 min if `image_size_gb` is not set). A candidate missing from vast's list is ended after 60 s grace. Blocklist: exit/error before enrollment → `network`; pull or enrollment timeout → `timeout`; worker kills (IP change, exit, no heartbeat) are not blocklisted. A slot becomes `up-to-date` at the first heartbeat. Test hooks: constructor kwargs `vast`, `ec2`, `clock`, `start_threads`. (Step 9)
