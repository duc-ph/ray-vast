# Decisions

The reasons for the design. The spec itself is in [design.md](design.md). Rule for every decision: the simplest option that works, with no loss of reliability and no fragility. A decision that a later one replaced is marked **Superseded**, with the line that replaced it.

## Base decisions (2026-10-12, before step 1)

| # | Question | Decision | Rejected |
|---|---|---|---|
| D1 | Where is the package? | `projects/ray-vast/` is a separate project, outside `badminton_ai`. The package is in `ray-vast-pypi/`. | — |
| D2 | Where does the enrollment and heartbeat server run? | A thread in the provider, in the monitor process. The autoscaler makes the provider only once, so there is no second object. If the monitor dies, the heartbeats stop too, and the workers destroy themselves after 5 min (cost safety over job continuity). | A separate daemon (Spark-style thin provider): more parts, and it only helps after a monitor crash, when the cluster cannot scale anyway. |
| D3 | Where is the state? | Memory only, plus a start-up sweep. A provider restart happens only with a head restart, and a new head has a new GCS, so old state has no use. The sweep is the same code as `down` and the orphan sweep. | SQLite on the head disk: more parts, and it cannot save the cluster because the GCS is lost anyway. |
| D4 | Where is the blocklist? | In memory, one for each cluster. A bad host costs less than $0.01 and 1–2 min, and the host checks run on every candidate anyway. A file across clusters is future work. | A file on the laptop or on the head: copy and merge code for a small saving. |
| D5 | What does `down` do with the head? | Terminate it, and delete the groups and the IAM role. Nothing is left. The CA key is lost, which agrees with "to renew, make a new cluster". | Stop the head and keep the groups: disk cost, and a second reuse path in `up` and `down`. |
| D6 | Does the head get an Elastic IP? | No. A reboot keeps the IP. After a stop and start, the user runs `down` and `up`. | An EIP: allocate and release code, a leak risk, for a cluster that is new anyway (D3). |
| D7 | Does Ray run as a different user than the image's user? | No. Ray runs as the image's user. The bootstrap keeps `CONTAINER_API_KEY` in memory for the destroy and removes it from Ray's env. A task can still read `/proc/1/environ` (documented risk; a task already has the token and the node cert, which give more). | Change to a non-root user on root images: file, `HOME` and device permission failures, for a small security gain. |
| D8 | How does a node type write its offer query? | The vast API JSON form, as a YAML mapping, MB units. No parser. `gpu_ram`/`cpu_ram` below 1000 is an error ("the unit is MB"). | Our own copy of the CLI parser (drift); `vastai`'s internal `parse_query` (unstable). |
| D9 | Which Ray versions? | The package requires `ray[default]>=2.59` (the image sets the version). `up` warns if the image's Ray is not in the tested list (now 2.59). | A hard pin (pip would change the image's Ray); an error for untested versions. |
| — | Which autoscaler? | v2 (F2 in design 3). | v1 (IP-unique node mapping). |
| S3 | Scoped vast key or a separate account for the head? | Neither. A thief on the head controls the cluster anyway, and vast's fixed key rights (change the account SSH keys) defeat a scope. Documented risk. | — |

## Log

- 2026-10-13 — The wheel is pure Python (`py3-none-any`) but carries the x86_64 Linux shim `.so` as package data. Reason: the `.so` is loaded only by `LD_PRELOAD` inside Linux containers, never imported; one wheel for all platforms. (Step 1)
- 2026-10-13 — The sdist includes only `src`, `tests`, `scripts` and the top-level files. Reason: keep spike logs and design docs out of the published package. (Step 1)
- 2026-10-13 — The packaging test installs the wheel with `--no-deps` and builds with `--no-isolation`. Reason: fast and offline; `--help` needs only the stdlib. The full Ray install is tested by the head container and the end-to-end tests. (Step 1)
- 2026-10-13 — Code review is run for each step that has logic; step 1 (packaging only) is reviewed with step 2.
- 2026-10-13 — `create_instance` retries only on HTTP 429. Reason: a lost answer may already have rented the offer; a retry could rent twice. The orphan sweep destroys a rental that we did not record. GET and DELETE retry on 429, 5xx and connection errors: 5 tries, backoff 1-2-4-8 s with jitter, 30 s per call. A destroy of an instance that is already gone (404) is a success. (Step 3)
- 2026-10-13 — `max_dollars_per_hour` is required (no default). Reason: a missing budget must not mean "no limit". `node_config.disk_gb` defaults to 50. The other provider fields have defaults (`candidate_factor` 2, `cert_max_age_days` 365, `allow_non_datacenter` false, `order_by` `dph_total`, `head_instance_type` `t3.large`). (Step 2)
- 2026-10-13 — A user filter on an added field (`cpu_cores_effective`, `direct_port_count`) is allowed when it is at least as strict, and it is merged; `num_gpus` must equal `GPU`. Reason: one node type for each CPU size (`{gte: 8, lt: 16}`). (Step 2)
- 2026-10-13 — The vast key is not a config field. The CLI reads it from `VAST_API_KEY` or `~/.config/vastai/vast_api_key`. Reason: keeps the secret out of the cluster YAML. The field is `cert_max_age_days`, for a clear unit. (Step 2)
- 2026-10-13 — PKI: RSA-2048 (proven with Ray gRPC in C0–C4); leaf certs have serverAuth and clientAuth; `not_before` 5 min in the past; CA `pathlen:0`; `cryptography>=42`. Fingerprint = SHA-256 of the CA DER, lowercase hex (S5). `ca.pem`/`head.pem` mode 644, keys and the token 600, the directory 700. A leaf cert never outlives the CA, so the expiry warning checks only the CA. (Step 4)
- 2026-10-13 — Two head server ports: TLS (download, enrollment) and mTLS (heartbeat, reports). Reason: one TLS context cannot ask for client certs on some paths only (S5).
- 2026-10-13 — State: the head is not stored in `ClusterState`; the provider adds the fixed `head` entry. A worker stays in `candidates` after enrollment (with `Slot.instance_id` set) until it is destroyed, so `total_dph` covers candidates and workers. `ip_ref_remove` stops at 0. Slot IDs are strings `slot-<n>-<hex6>` (v2 accepts any string). A candidate's `public_ip` is set once, at the first `running`, and never refreshed; the provider compares it with vast's current IP to find an IP change. SG method names: `allow_ip`/`revoke_ip`/`revoke_all`. (Steps 5–6)
- 2026-10-13 — **Superseded** by "up to 5 security groups": one security group for each cluster (about 59 worker IPs). (Step 6)
- 2026-10-13 — Provider: one request = the slots of one create call; its candidates are spread over its slots; when every slot of a request is filled, its other unenrolled candidates are destroyed. Pull limit = `2 × image_size_gb × 8000 / inet_down` s, 5–15 min (15 min if `image_size_gb` is not set). A candidate missing from vast's list is ended after 60 s. Blocklist kinds: exit or error before enrollment → `network`; pull or enrollment timeout → `timeout`; the end of an enrolled worker → no blocklist. A slot becomes `up-to-date` at the first heartbeat. Test hooks: constructor kwargs `vast`, `ec2`, `clock`, `start_threads`. (Step 9)
- 2026-10-13 — The full Ray v2 autoscaler scenarios (scale up 3 with k=2, idle scale-down, a candidate that never enrolls, a shared IP) move from step 9 to step 11 (local end-to-end with real raylets). Step 9 keeps a `NodeProviderAdapter` compatibility test. Reason: they need real Ray nodes. (Step 9)
- 2026-10-13 — Head server: refusals before the identity proof (unknown instance, already enrolled, wrong source IP) give 403 without a destroy, so a stranger who knows an instance ID cannot kill a candidate. Failed host checks blocklist as `security` (caps, netns, shm) or `network` (egress, port check). Port-A `/report` is only logged. `num_workers_soft_limit = min(cpu_count, 58)`. (Step 8)
- 2026-10-13 — **Superseded** by the join token: the identity proof was the worker's `CONTAINER_API_KEY`, which the head checked with `GET /instances/<id>/` on vast. A bad key (vast 401/403/404) gave 403 without a destroy, and a vast outage gave 503. (Step 8)
- 2026-10-13 — Node certs carry a URI SAN `rayvast:instance/<id>`; port B checks it and the IP SAN. Reason: IP-only certs let a worker, or a former holder of a re-rented IP, send heartbeats or a failed token check for another instance on the same IP. Also: 64 different ports are required; the node cert is made before the instance is marked enrolled. (Step 8)
- 2026-10-13 — The bootstrap builds the CA PEM again from the hashed DER and refuses a `/ca.pem` with more than one cert. Reason: Python's lenient base64 decode let "real CA + rogue CA" pass the fingerprint while OpenSSL trusted both. (Step 7)
- 2026-10-13 — Worker: every HTTP call has a wall-clock limit; the bootloader never exits (it retries, and after a hash mismatch or 10 min of failures it destroys its own instance); vast calls do not follow redirects; the token check retries statuses that are not 401. (Step 7)
- 2026-10-13 — The NET_RAW/NET_ADMIN host check reads `CapBnd`, not `CapEff`. Reason: a non-root PID 1 always has an empty `CapEff`, so the old check never failed. (Step 7)
- 2026-10-13 — **Superseded** by "no head self-healing": the head container ran with `docker run --restart unless-stopped`, so Docker restarted a head whose monitor died (S2).
- 2026-10-13 — CLI: `up` builds the wheel on the laptop (or takes `--wheel`), copies it to the head and builds a derived image `FROM <image>` plus the wheel. `cli.py` only parses arguments; `commands.py` does the work (so `--help` needs no boto3). Reviewed with the user: local wheel now; after the PyPI release, `up` installs `ray-vast==<the CLI's own version>` by default and keeps `--wheel` for development. (Step 10)
- 2026-10-13 — `down` terminates the head first, then sweeps vast, then deletes the groups and IAM. Reason: a live head autoscaler could rent new workers during the sweep. `--key-name`/`--key-file` (or `provider.key_name`/`key_file`) select the SSH key; they are removed from the YAML on the head. One `known_hosts` file for each cluster, with `accept-new`. Cluster names match `[A-Za-z0-9][A-Za-z0-9_-]{0,39}`. (Step 10)
- 2026-10-13 — `down` without a vast key cleans AWS, warns that vast instances were not swept (with the commands to do it) and exits 0. `up` on an existing cluster name stops before it makes anything. `up` writes the measured `image_size_gb` into the head config; a user value wins. `ray-vast dashboard` copies the cluster token to `~/.ray-vast/<cluster>/token` (600) and prints the `RAY_AUTH_MODE=token RAY_AUTH_TOKEN_PATH=…` line. (Step 10)
- 2026-10-13 — Live cycles use only the real CLI and the real provider: no second "harness" provider in the head and no proxy that changes vast answers. C7 (forced IP change) is not run live: real vast cannot force an IP change; unit tests and step 11 cover it. T14 blocks port B on the head with iptables. The restart test uses vast's reboot call. T15 runs on `rayproject/ray` (non-root) only. Reviewed with the user: live = C5 join and task, C6 self-destroy paths, C8 full scale; not live = IP change, other images, attack cases. (Step 12)
- 2026-10-13 — Candidates: k = 2 (`candidate_factor`) and the pull and enrollment limits are confirmed with the user.
- 2026-10-13 — Up to 5 security groups for each cluster (reviewed with the user). `up` makes `ray-vast-<cluster>-0` … `-4` (tagged), all on the head's network interface (the AWS default limit is 5 groups for one interface); group 0 also holds the SSH rule. A rule goes into the first group with room (on `RulesPerSecurityGroupLimitExceeded` it tries the next). Capacity with the default quota of 60 rules: about 299 worker IPs. Rejected: one group (about 59 IPs); an open head (a DDoS on the head stops the cluster).
- 2026-10-13 — No head self-healing (reviewed with the user: "keep it simple, leave the head hanging"). The head container runs `ray start --head --block` with no Docker restart policy. If the monitor dies, Ray stops the head, every worker destroys itself within 5 min, and the EC2 head stays until `down`. Same result as standard `ray up` clusters. Rejected: a Docker restart of the whole head; a KubeRay-style separate autoscaler container (needs a provider that rebuilds its state from vast; future work).
- 2026-10-13 — Enrollment identity proof: a one-time join token (C5a/C5d live finding; agreed with the user). vast answers the head's `GET /instances/<id>/` with HTTP 401 when the head sends the worker's `CONTAINER_API_KEY`. The `kubeadm join --token` pattern replaces it: the provider makes a random token for each candidate and puts it in the create env; the head accepts it only for that instance ID, from that instance's IP, once. Rejected: a nonce on the identity ports (anyone can read and replay it); an HMAC challenge (works, but an invented protocol with more code). `CONTAINER_API_KEY` never leaves the worker. The 64-port check stays a plain reachability check.
- 2026-10-13 — Rent-loop breaker (C5a live finding; agreed with the user): for each node type, count the slots that end with no enrolled worker; a successful enrollment resets the count. After 3 failed slots in a row, refuse new launches of that node type for 10 min (`NodeLaunchException`, logged at ERROR), then try again.
- 2026-10-13 — Docs: one topic in one file. `protocol.md` is merged into `design.md` section 5; the plan's Ray facts are design section 3; the plan's D1–D9 are in this file; the test levels and the live cycles are in `test-plan.md`. "Port check" (the head connects to the 64 ports) and "orphan sweep" (the provider destroys unknown labelled instances) replace the two meanings of "outside check".
- 2026-10-14 — `/enroll` gives 403 without a destroy for a missing, empty or non-string `join_token`, the same as a wrong token. It gives 503 only when the provider has not seen the candidate `running` yet (no public IP). The 503 check comes after the "unknown" and "already enrolled" checks. (Step 10b)
- 2026-10-14 — Rent-loop breaker count: a slot fails only when the reconcile pass removes a free slot because no pending candidate of its node type is left. A create that rents nothing and a terminate from the autoscaler are not failures. An enrollment sets the count to 0. A trip also sets the count to 0, so after the 10 min pause 3 new failures are necessary to trip again. (Step 10b)

Container names in the tests start with `<step>-<pid>-`, and the session leak check removes only the containers of its own run. Reason: the old fixed prefix let one test run remove the containers of a parallel run. (Step 10b)

- 2026-10-14 — GPU count (C5 live finding): the worker counts the `/dev/nvidia<N>` device nodes of its container, not `/proc/driver/nvidia/gpus` (that showed the host's 4 GPUs on a 1-GPU rental). The head refuses a count other than the node type's `GPU` in both directions, destroys the instance and blocks the host as `security`. Reason: fewer GPUs is a broken host; more can be another tenant's GPUs. The provider keeps the declared count on the candidate; the answer's `num_gpus` is that count. (Step 12)
- 2026-10-14 — The head container gets `--shm-size` = 0.33 × the head's RAM, read on the head when `up` starts it. Reason: Ray's object store falls back to `/tmp` with Docker's 64 MB default; 0.33 is Ray's launcher rule (0.3 × 1.1), and it follows any head instance type. (Step 12)
- 2026-10-14 — The minimum internet speed (`inet_down`, `inet_up` ≥ 500 Mb/s) is only in the live test YAMLs, not in the product (the user's choice). A cluster YAML can set these vast fields in `offer_query`. (Step 12)
- 2026-10-14 — Design review (agreed with the user): one function ends a candidate or worker for both the provider and the head server (remove from state with its slot, block the host, destroy on vast, lower the IP ref count, revoke the SG rule at 0). One sweep function serves the start-up sweep, the orphan sweep and `down`, and one helper builds the `ray-vast:<cluster>` label, so D3 is true again. A state-owned lifecycle and a thinner head server are future work. After the change, step 11 and the live cycles C5, C6 and C8 run again.
- 2026-10-14 — Design review, how it was built. `_end` and `sweep` catch every error of a destroy and do not raise. They log the text of a `VastError` (redacted by `vast_api`) and only the type of any other error. Reason: their callers are the reconcile pass, the head server's request threads and `down`, and a failed destroy must not skip the rule removal. `sweep(vast, instances, cluster, keep)` takes the instance list from the caller. Reason: the orphan sweep must judge its `keep` set against the list of the same reconcile pass; a new list could show a rental that a create call has not recorded yet. `label(cluster)` and `sweep` are in `vast_api.py`. The SG rule description uses `label(cluster)` too: it is the same cluster marker (design 8.3). `up` keeps the image's ENTRYPOINT and reads only the line `RAYVAST_IMAGE_INFO <ray version> <shim path>` from the image check (C8).
- 2026-10-14 — Review of the refactor: `_end(cand, reason, block_kind)` takes the candidate and blocks the host on every call, also when another caller ended the candidate first. `_end` never raises: a failed destroy or a failed SG revoke (`ClientError` or `BotoCoreError`) is logged by type and code. A revoke that failed is retried on each reconcile pass until it works or the IP is in use again. Reason: without the retry, the rule stayed until `down`. (Step 12)

- 2026-10-14 — User docs: a MkDocs Material site in the Diátaxis layout (getting started, how-to, reference, explanation), published by a GitHub Actions workflow to GitHub Pages (source set to GitHub Actions by the user). The README becomes a short front page with absolute links. Test commands move to `CONTRIBUTING.md`. (Step 13)
- 2026-10-14 — `up` without a wheel (agreed with the user): `pip install ray-vast` then `ray-vast up` must work. The head's derived image runs `pip install ray-vast==<the CLI's own version>` (`ray_vast.__version__`, the single source of the package version). Order: `--wheel FILE` > `--index-url URL` > the source tree (builds the wheel, for development) > PyPI. `--index-url` adds `--extra-index-url https://pypi.org/simple`, because TestPyPI lacks the dependencies. `--index-url` beats the source tree. Thus a test of a TestPyPI release from a git clone uses the release, not the local code. `--wheel` with `--index-url` is an error. `--index-url` must be a plain `http://` or `https://` URL with no spaces: a newline would start a new Dockerfile instruction. `up` masks a user name and a password in the URL in its output. The URL stays in the image's build history, so the docs tell the user not to put credentials in it. A failed `docker build` on the index path stops `up`. The message names the version and the index, and it does not guess the cause. The version is `0.1.0rc1` for TestPyPI (it refuses a second upload of one version) and `0.1.0` for PyPI; `requires-python >=3.10` (Ray 2.59). `build` stays in the `test` extra only: just the source-tree path needs it. (Step 13)
- 2026-10-14 — The pids limit (C9 live finding): vast containers have `pids.max` 1280 on many hosts; gRPC sizes its thread pools in every Ray process by the host's core count, so a Ray Data job with all CPUs goes past the limit and the node dies. **Superseded** by the 2026-10-16 line (design (a)). Was open: branch `pids-limit-review` (shim v4 reports 4 processors to gRPC and all other code in the worker; and a cap of Ray CPUs and worker ports by `pids.max`, a change of F4). Until then, the user docs give a Ray Data CPU limit as the workaround. The two small bugs of C9 (a failed thread start ends a worker; the destroy reason lost its error line) are fixed on `main`. (Step 12)
- 2026-10-16 — The process limit (`pids.max`): design (a), agreed with the user. Details: design.md 5.5 and 5.7a.
    - The worker starts Ray with `RAY_num_grpc_internal_threads=4` and `RAY_worker_maximum_startup_concurrency=8`. Both are always set.
    - Worker ports = `max(4, min(58, (pids.max − 400) // 60))`. Without a limit, 58. `RAY_num_workers_soft_limit` = min(Ray CPUs, worker ports // 2). (The first version used 35 and min(Ray CPUs, worker ports); see the tuning bullets below.)
    - Ray CPUs stay the real core count. F4 does not change.
    - The bootstrap decides these values. The `/enroll` answer no longer has `num_workers_soft_limit`.
    - The heartbeat carries `pids_current`, `pids_max`, `pids_refused`, `ports_in_use` and `ports_total`. The head logs one WARNING line for a worker. On new refusals, at most once a minute. When all ports are in use or pids are above 90 %, at most once in 5 minutes.
    - Measurement setup: a simulated 48-core worker. `rayproject/ray:2.59.0-py311-cpu`, `docker run --pids-limit 1280`, `--num-cpus 48`, and a test `LD_PRELOAD` that makes `sysconf` and `get_nprocs` report 48.
    - Threads: a worker process has 50 threads by default, and 25 to 28 with gRPC threads 4. The raylet has 85, and 59 to 66 with gRPC threads 4. The fixed Ray processes have about 150.
    - The startup variable wins over the `ray start` flag. With the value 2, at most 2 processes started at the same time. Without it, 39.
    - Before (58 ports, no startup cap, gRPC threads 4): 48 tasks of 1 CPU reached 1280. `pids.events` showed `max 269`.
    - First version (35 threads per process), with 25 ports and the startup cap 8: `pids.events` stayed at `max 0` in every run, and the worker never died. 400 tasks of 0.05 CPU: PASS, peak 843. 60 actors with default CPUs: 25 ran, the others waited (`No available ports`), peak 862.
    - First version: Data `groupby` (97 partitions) on 48 CPUs hung, peak 887. The map-side shuffle tasks held all 25 ports, so the aggregator actors got none. With `max_hash_shuffle_aggregators=4` only, it also hung (peak 888). With that and `resource_limits cpu=16`: PASS in 36 s, peak 830.
    - First version, with pids.max 3328 (58 ports): 400 tasks of 0.05 CPU: PASS. 60 actors: 58 ran, and 2 failed after 415 s with `ActorUnschedulableError` (no free port). Peak 1779, `max 0`.
    - Reasons: the port count is a hard cap on registered worker processes. So too much work becomes a queue, not a crash. The CPUs stay correct for the autoscaler.
    - Rejected: shim v4. It fakes `sysconf` for all code, also user code. A Ray setting does the same for gRPC only.
    - Rejected: the CPU cap of `pids-limit-review`. It changes F4, and v2 then plans with wrong CPUs.
    - Tuning (same day, after local C10 checks): the first version had two faults.
    - Fault 1: idle worker processes held all ports. The raylet keeps idle worker processes while their count is at or below the soft limit. It never ends an idle worker process to free a port. With 25 ports and the soft limit 25: 60 tasks left 25 idle worker processes, and 4 tasks with another runtime env waited until the timeout. With the soft limit 12 or 6: PASS. Decision: soft limit = min(Ray CPUs, ports // 2).
    - Fault 2: 35 threads per port was too few for Serve. Threads per process with gRPC threads 4 on a simulated 48-core host: a Serve replica with FastAPI 50 (its Python `grpcio` adds an event-engine pool of 16), the Serve proxy 35, a Ray Train worker process 35, plus 3 for each `DataLoader` worker process, a Data actor 29, an RLlib env runner 28, a task or an idle worker process 25 to 28. The C10 check saw 60 Serve replicas of 0.1 CPU crash a worker with 24 ports (a failed fork ends the raylet). Decision: 60 per port (the Serve replica plus 10 of the user's threads). Reserve stays 400: about 160 fixed, 8 × 25 starting processes (also the ones that find no port), 40 of headroom.
    - Result: 14 ports at 1280, 48 at 3328, soft limit 7 and 24 (with 48 CPUs).
    - Proof setup: a separate head container, a worker with `--pids-limit 1280`, 48 CPUs, 14 ports and the soft limit 7. In every run, `pids.events` stayed at `max 0`, and the worker never died.
    - Serve, 60 replicas of 0.1 CPU, 3 runs: the application stayed in DEPLOYING (a hang). Peaks 860, 860 and 864.
    - Train, 2 workers with `DataLoader(num_workers=2)`: PASS, peak 228.
    - 400 tasks of 0.05 CPU: PASS, peak 542.
    - 60 actors: 14 ran, and the others waited. Peak 562.
    - Data `groupby` with 4 aggregators: PASS with `cpu=12` (peak 584) and with `cpu=16` (peak 586).
    - Two runtime envs (fault 1): PASS, peak 539.
    - RLlib PPO with 4 env runners: PASS, peak 256.
